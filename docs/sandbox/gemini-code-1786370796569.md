# OpenCode Loop-Engineering Implementation Plan
**Objective:** Transition the `opencode` agent from turn-by-turn manual prompting to an autonomous, loop-driven architecture for daily triage and basic coding tasks.

---

## Phase 1: Core Infrastructure & State Management
Before the agent can loop, it needs a persistent memory structure to survive session restarts and avoid token bloat.

*   **Initialize Loop Directories:** Run `npx @cobusgreyling/loop init .` to generate the foundational files.
*   **Establish State Files:** 
    *   Create `LOOP-STATE.json` for machine-readable state tracking (current active task, retry counts, budget).
    *   Create `STATE.md` for human-readable context (e.g., current architecture rules like enforcing Clean Architecture layers, or offline-first synchronization protocols).
*   **Configure OpenCode Agent:** Map the `opencode` capabilities to the loop environment by linking `.opencode.json` to the loop harness.

## Phase 2: The Daily Triage Loop
This loop wakes up on a schedule to assess the repository, categorize issues, and prepare the workspace.

*   **Trigger Mechanism:** Set up a cron job or a GitHub Action scheduled for the start of the day.
*   **Agent Task (The Scout):** 
    *   Scan newly opened issues and recent crash logs.
    *   Apply automated labels based on stack traces (e.g., tagging UI layer bugs involving `BuildContext` or `GlobalKey`, versus data layer bugs involving local cache/offline-sync failures).
*   **Output:** Update `STATE.md` with a prioritized daily task list.

## Phase 3: The CI Sweeper Loop
This loop acts defensively, waking up when the automated CI/CD pipelines fail.

*   **Trigger Mechanism:** Webhook from the CI/CD mobile deployment pipeline upon a failed build or test suite.
*   **Agent Task (The Fixer):**
    *   Ingest the failed CI logs.
    *   Spin up an isolated `git worktree` to avoid disrupting the main branch.
    *   Attempt a fix (e.g., resolving a dependency conflict or a failed unit test in the domain layer).
*   **Verification Gate:** Run the local test suite. If it passes, commit and push to a new fix branch. If it fails twice, halt and update `STATE.md` for human review.

## Phase 4: The Maker/Checker Split (Verification Gate)
To safely reach Level 3 autonomy, the system must never push unverified code.

*   **The Maker (`opencode` primary):** Drafts the code changes.
*   **The Checker (`loop-verifier`):** A secondary lightweight agent prompt strictly tasked with reviewing the diff against the repository's `.opencode/skills/` definitions (e.g., ensuring no business logic leaked into the presentation layer).
