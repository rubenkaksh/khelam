# ER Diagram — RMS Futsal Booking Platform

```mermaid
erDiagram
    OWNERS ||--o{ TURFS : owns
    TURFS ||--o{ SLOTS : has
    TURFS ||--o{ BOOKINGS : receives
    USERS ||--o{ BOOKINGS : makes
    SLOTS ||--|| BOOKINGS : "reserved by"
    BOOKINGS ||--o{ PAYMENTS : "paid via"
    USERS ||--o{ NOTIFICATIONS : receives
    BOOKINGS ||--o{ NOTIFICATIONS : triggers
    USERS ||--o{ OTP_VERIFICATIONS : requests

    USERS {
        uuid id PK
        varchar phone_number UK
        varchar full_name
        varchar email
        boolean is_active
    }

    OWNERS {
        uuid id PK
        varchar phone_number UK
        varchar full_name
        text password_hash
    }

    ADMINS {
        uuid id PK
        varchar email UK
        text password_hash
    }

    TURFS {
        uuid id PK
        uuid owner_id FK
        varchar slug UK
        varchar name
        text address
        numeric price_per_hour
        numeric advance_amount
        time opening_time
        time closing_time
        numeric rating
    }

    SLOTS {
        uuid id PK
        uuid turf_id FK
        date slot_date
        time start_time
        time end_time
        varchar status
        uuid locked_by FK
        timestamptz locked_at
    }

    BOOKINGS {
        uuid id PK
        varchar booking_code UK
        uuid user_id FK
        uuid turf_id FK
        uuid slot_id FK
        numeric total_amount
        numeric advance_amount
        numeric remaining_amount
        varchar status
    }

    PAYMENTS {
        uuid id PK
        uuid booking_id FK
        varchar gateway
        numeric amount
        varchar transaction_id
        varchar status
    }

    OTP_VERIFICATIONS {
        uuid id PK
        varchar phone_number
        text otp_hash
        boolean is_used
        timestamptz expires_at
    }

    NOTIFICATIONS {
        uuid id PK
        uuid user_id FK
        uuid booking_id FK
        varchar type
        boolean is_sent
    }

    AUDIT_LOGS {
        uuid id PK
        varchar actor_type
        uuid actor_id
        varchar action
        varchar entity_type
        uuid entity_id
    }
```

### Key relationships
- **One owner → many turfs** (already modeled, even though only 1 turf exists today).
- **One turf → many slots**, one row per bookable hour per date. Slots are
  generated by a scheduled job that keeps a rolling 3-day window populated.
- **One slot → at most one active booking** — enforced at the application layer
  via the locking flow (see `booking_service.py`) and at the DB layer via the
  `UNIQUE (turf_id, slot_date, start_time)` constraint on `slots`.
- **One booking → one or more payment attempts** (a failed eSewa attempt
  followed by a successful Khalti retry both live in `payments`, so the audit
  trail is never lost).
